## Architecture
- Storefront: catalogue lives in `src/lib/catalog.ts`, cart/wishlist/account/panel state in `src/lib/store.tsx`. Signed-in shoppers' bag and wishlist, plus the newsletter and pincode check, go through `src/lib/api.ts` to the API; guests (and a build with `VITE_API_URL` set to an empty value) use localStorage. A production build with `VITE_API_URL` unset talks to `https://api.leatherluxindia.com` (default in `src/lib/api.ts`; deployment steps in `server/deploy/README.md`). Checkout (`/checkout`) and order history (`/orders`) use the API (no payment is collected yet). The product list comes from the API via `src/lib/catalog-live.ts` (`useCatalog()`), falling back to the built-in `src/lib/catalog.ts` when the API is unreachable; read products through `useCatalog()`, not the static `PRODUCTS`, so prices/stock/visibility stay live. The page first renders from the built-in list as placeholder data, which is NOT the live list: `useCatalog().settled` is false until the live list (or an error) arrives, and a page that can find only database products (the 76 photographed ones) must wait on it or use what its loader read, never show "not found" on the placeholder. The product page renders the product its loader returned until the live list is in.
- `server/` is a separate Node/Express + Postgres (EC2) API with its own `package.json`, `.env` and tests; it is excluded from the frontend's eslint/prettier and is never bundled by Vite. See `server/README.md`. Never commit `server/.env`. Roles are rows in the `roles` table (`admin`, `user`); the admin console lives at `/admin` (`src/routes/admin*.tsx`) and edits branding, offers, loyalty and discount rules, which are stored but not yet applied at checkout. The store name and logo come from the API via `src/lib/brand.tsx`; never hard-code the brand name in UI text or page titles. Admin accounts are added only with `npm run admin:add` (default password `Admin@2026`, forced change at first sign-in); the website has no admin sign-up. Server logs go to dated files in `server/logs/` (`app-` and `error-`). Caching: the API caches catalogue, branding, visitor total and signed-in users in memory (`server/src/lib/caches.ts`); any new API write that changes products/stock, branding, users' password/sessions or visitors MUST call the matching `invalidate…()`, and never cache per-user data (bag, wishlist, orders). Inventory and photos: a product's `images` are bundled-asset keys (the 22 starter products) or `/media/…` paths served by the API from `server/media/` (git-ignored; made by `npm run products:import` from `server/data/catalogue/*.json`); always turn one into a URL with `imageUrl()` in `src/lib/catalog-live.ts` and use `productThumb()` for small images. What shoppers see is two settings: `active` (false = hidden altogether) and `availability` (`active`, `inactive` or `coming_soon`). An inactive or coming-soon product stays listed, but the API reports `stock: "out"` for it and refuses it in the bag and in orders; coming soon also gets a label and the Coming Soon collection and nav link (shown only while something is coming soon). The admin row has one select for this (Active, Inactive, Coming soon, Hidden; `statusOf`/`statusPatch` in `src/components/admin/inventory-types.ts`). `hover_effect` (swap, slide, zoom, none) drives `HoverImage` on product cards. The Add product form (`AddProduct.tsx`) takes 1 to 4 photos, resized in the browser (`src/lib/photo-upload.ts`, with the backdrop recolour in `src/lib/photo-backdrop.ts`, a copy of `server/src/lib/photo-background.ts`) and stored in the `product_photos` table because Vercel's disk is read-only; they are served at `/api/photos/<id>` (and `/thumb`) and a product refers to them as `/api/photos/<id>` in `images`. The inventory totals have a row of status filters and a row of rupee cards (units, stock at shop price, stock at cost, profit on stock; the last two count only products that have a cost). The margin shown in an inventory row is read-only (worked out from price and cost); price, cost and the stock count are editable in the row, and a stock edit goes through the ledger as a correction. Every stock change must go through `server/src/lib/inventory.ts` so it reaches the `inventory_movements` ledger; the Inventory admin page is `src/routes/admin.inventory.tsx` + `src/components/admin/ProductEditor.tsx`. Motion: use the `ease-lux` easing and the shared `Drawer`/`Reveal`/`Img` components; respect `prefers-reduced-motion`. Every hero banner (the home hero and the collection banners) is a `LiveHero` (`src/components/site/LiveHero.tsx`): a slow CSS drift and a periodic band of light (`.anim-hero-*` in `src/styles.css`), plus pointer parallax and a following glow for mouse users (`useHeroMotion` in `src/lib/hero-motion.ts`; off for touch and reduced motion). A new hero must use `LiveHero` so they all move alike. Rollback points: git tags `hero-static-2026-11-02` (no live hero) and `heroes-home-only-2026-11-02` (only the home hero live).
- Pre-launch notice ("opening this Christmas"): wording and the on/off switch are in `src/lib/launch.ts` (`LAUNCH.enabled`); it shows in the top bar (`Header.tsx`) and as `LaunchBand` (`src/components/site/LaunchNotice.tsx`) under the home hero. Set `enabled: false` on launch day. Placing orders is a separate, server-enforced switch: `ORDERS_OPEN` in `server/.env` (false = `POST /api/orders` answers 403 `orders_closed`); the storefront follows `GET /api/store-status` through `useOrdersOpen()` in `src/lib/store-status.ts`, so never offer a checkout path without checking it.
- Deployment: ONE Vercel deployment serves the storefront and the API on the same domain. `npm run build` runs `vite build`, then `scripts/vercel-api.mjs` (Vercel only) bundles `server/src/vercel.ts` into an `api` function and routes `/api/*` to it; product photos are static files in `public/media/`. The browser calls `/api` on its own origin (`src/lib/api.ts`; server rendering uses `SITE_URL` or `VERCEL_PROJECT_PRODUCTION_URL`). Serverless rules for server code: the visitor's real IP only exists because the API trusts Vercel's X-Forwarded-For (`TRUST_PROXY` is raised to at least 1 when `VERCEL` is set, in `parseEnv`, because the live project had it typed in as 0; without it every visitor would be `127.0.0.1` in the visit log and share one rate-limit bucket), no log files (`LOG_TO_FILES=false`), no state kept in memory that must be shared (sign-in/register/newsletter/visit limits use `RATE_LIMIT_STORE=postgres`), a tiny DB pool, and a database connection verified against the pinned certificate (`DB_SSL_CA`). Settings for Vercel: `server/deploy/vercel.env.example`; setup and limits: `server/deploy/VERCEL.md`.
- Security: production responses carry a content-security policy and other browser-hardening headers from `src/lib/security-headers.ts`, applied in `src/server.ts` (production builds only). Anything new the site loads from another host (analytics, maps, fonts, images) must be added there, or the browser will block it. API hardening, backups and the live-deployment check (`server/deploy/check-security.sh`) are in `server/deploy/README.md`.
- Search engines: every page names ONE canonical address (`SITE_ORIGIN` in `src/lib/seo.ts`, set in the root route's `head`), because the shop answers on several domains; the home page carries `WebSite`/`Organization` structured data; `/sitemap.xml` is built from the live catalogue (`src/routes/sitemap[.]xml.tsx`); `public/robots.txt` keeps /admin, /checkout, /orders and /api out of search. The site icon is a fixed set of square files in `public/` (`favicon.ico`, `favicon-96x96.png`, `apple-touch-icon.png`) made from the logo by `scripts/make-favicons.mjs`, NOT the uploaded logo (Google only accepts a square icon, a multiple of 48 px); regenerate them if the logo changes. Bing and Google setup, and `scripts/indexnow.mjs`, are in `docs/search-engines.md`. A new public page needs no extra work, but a new private page must be `noindex` and listed in robots.txt. Pictures: every page has an `og:image`/`twitter:image` from `imageMeta()` in `src/lib/seo.ts` (the hero by default in the root route; a page with its own picture, such as a product or a collection, replaces it); product pages carry `Product` JSON-LD from `productJsonLd()` only once `LAUNCH.enabled` is false (before that it returns null: Google rejects a Product without a price, nothing can be bought yet, and the page's reviews are samples); `/sitemap.xml` is built by `buildSitemap()` (`src/lib/sitemap.ts`) with each page's pictures; `robots.txt` must keep `Allow: /api/photos/` so Google Images can fetch admin-uploaded photos. See `docs/search-engines.md`.
- Dropdowns: never use a native `<select>` or `<datalist>` (they look different on every device and cannot be styled). Use `Select` (choose one option; a search box appears for lists over 8) or `Combobox` (a text field with suggestions, for free text such as a category) from `src/components/ui/select-menu.tsx`; their look and motion are the `.menu-*` rules in `src/styles.css`.
- Validation: what a shopper types (name, mobile number, pincode, address lines, city, state, email) is judged by the rules in `src/lib/validation.ts`, which is the SAME file as `server/src/lib/validation.ts` (the browser shows the message, the server enforces it; `src/test/validation.test.ts` fails if they differ, so change both and add a case). Use them for any new field of that kind; never write a new regex in a component. The checkout fills city and state from the pincode (`usePincodeLookup` in `src/lib/pincode.ts`, served by `GET /api/pincode/:pin`, which reads India Post's public data and never blocks an order). A table of every rule, with before and after, is `docs/validation.md`.
- Visit log: every page view is recorded in the `visit_log` table (IP address, path, time, browser, referrer origin, `is_bot`) by `POST /api/visits/log`, called from `PageViewLogger` in `src/routes/__root.tsx` (`src/lib/page-view.ts`; not for `/admin`). It holds personal data: keep it out of every public API and every log or screenshot, keep the retention (`VISIT_LOG_RETENTION_DAYS`), and see `docs/visit-log.md` for the columns, queries and privacy checklist. The footer's "Total visitors" is separate: `site_counters`, +1 on every page load.
- Site chrome (header, drawers, footer, toaster) is mounted once in `src/routes/__root.tsx`; pages only render content.
- Shared visual primitives are `@utility` classes in `src/styles.css` (btn-ink, btn-outline, eyebrow, link-line); use them instead of ad-hoc button styles.
