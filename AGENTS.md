## Architecture
- Storefront: catalogue lives in `src/lib/catalog.ts`, cart/wishlist/account/panel state in `src/lib/store.tsx`. Signed-in shoppers' bag and wishlist, plus the newsletter and pincode check, go through `src/lib/api.ts` to the API; guests (and a build with `VITE_API_URL` set to an empty value) use localStorage. A production build with `VITE_API_URL` unset talks to `https://api.leatherluxindia.com` (default in `src/lib/api.ts`; deployment steps in `server/deploy/README.md`). Checkout (`/checkout`) and order history (`/orders`) use the API (no payment is collected yet). The product list comes from the API via `src/lib/catalog-live.ts` (`useCatalog()`), falling back to the built-in `src/lib/catalog.ts` when the API is unreachable; read products through `useCatalog()`, not the static `PRODUCTS`, so prices/stock/visibility stay live.
- `server/` is a separate Node/Express + Postgres (EC2) API with its own `package.json`, `.env` and tests; it is excluded from the frontend's eslint/prettier and is never bundled by Vite. See `server/README.md`. Never commit `server/.env`. Roles are rows in the `roles` table (`admin`, `user`); the admin console lives at `/admin` (`src/routes/admin*.tsx`) and edits branding, offers, loyalty and discount rules, which are stored but not yet applied at checkout. The store name and logo come from the API via `src/lib/brand.tsx`; never hard-code the brand name in UI text or page titles. Admin accounts are added only with `npm run admin:add` (default password `Admin@2026`, forced change at first sign-in); the website has no admin sign-up. Server logs go to dated files in `server/logs/` (`app-` and `error-`). Caching: the API caches catalogue, branding, visitor total and signed-in users in memory (`server/src/lib/caches.ts`); any new API write that changes products/stock, branding, users' password/sessions or visitors MUST call the matching `invalidate…()`, and never cache per-user data (bag, wishlist, orders). Inventory and photos: a product's `images` are bundled-asset keys (the 22 starter products) or `/media/…` paths served by the API from `server/media/` (git-ignored; made by `npm run products:import` from `server/data/catalogue/*.json`); always turn one into a URL with `imageUrl()` in `src/lib/catalog-live.ts` and use `productThumb()` for small images. Every stock change must go through `server/src/lib/inventory.ts` so it reaches the `inventory_movements` ledger; the Inventory admin page is `src/routes/admin.inventory.tsx` + `src/components/admin/ProductEditor.tsx`. Motion: use the `ease-lux` easing and the shared `Drawer`/`Reveal`/`Img` components; respect `prefers-reduced-motion`.
- Pre-launch notice ("opening this Christmas"): wording and the on/off switch are in `src/lib/launch.ts` (`LAUNCH.enabled`); it shows in the top bar (`Header.tsx`) and as `LaunchBand` (`src/components/site/LaunchNotice.tsx`) under the home hero. Set `enabled: false` on launch day. Placing orders is a separate, server-enforced switch: `ORDERS_OPEN` in `server/.env` (false = `POST /api/orders` answers 403 `orders_closed`); the storefront follows `GET /api/store-status` through `useOrdersOpen()` in `src/lib/store-status.ts`, so never offer a checkout path without checking it.
- Deployment: ONE Vercel deployment serves the storefront and the API on the same domain. `npm run build` runs `vite build`, then `scripts/vercel-api.mjs` (Vercel only) bundles `server/src/vercel.ts` into an `api` function and routes `/api/*` to it; product photos are static files in `public/media/`. The browser calls `/api` on its own origin (`src/lib/api.ts`; server rendering uses `SITE_URL` or `VERCEL_PROJECT_PRODUCTION_URL`). Serverless rules for server code: no log files (`LOG_TO_FILES=false`), no state kept in memory that must be shared (sign-in/register/newsletter/visit limits use `RATE_LIMIT_STORE=postgres`), a tiny DB pool, and a database connection verified against the pinned certificate (`DB_SSL_CA`). Settings for Vercel: `server/deploy/vercel.env.example`; setup and limits: `server/deploy/VERCEL.md`.
- Security: production responses carry a content-security policy and other browser-hardening headers from `src/lib/security-headers.ts`, applied in `src/server.ts` (production builds only). Anything new the site loads from another host (analytics, maps, fonts, images) must be added there, or the browser will block it. API hardening, backups and the live-deployment check (`server/deploy/check-security.sh`) are in `server/deploy/README.md`.
- Search engines: every page names ONE canonical address (`SITE_ORIGIN` in `src/lib/seo.ts`, set in the root route's `head`), because the shop answers on several domains; the home page carries `WebSite`/`Organization` structured data; `/sitemap.xml` is built from the live catalogue (`src/routes/sitemap[.]xml.tsx`); `public/robots.txt` keeps /admin, /checkout, /orders and /api out of search. A new public page needs no extra work, but a new private page must be `noindex` and listed in robots.txt.
- Site chrome (header, drawers, footer, toaster) is mounted once in `src/routes/__root.tsx`; pages only render content.
- Shared visual primitives are `@utility` classes in `src/styles.css` (btn-ink, btn-outline, eyebrow, link-line); use them instead of ad-hoc button styles.
